# Further GPU-to-CPU handoff improvements

These are source-backed proposals, not implemented or measured gains. Keep them out of the pending CPU/copy/share long-task comparison so routing remains the only variable. Existing zero-copy and allocation-level view batching remain the controls.

## Priorities

1. **Reuse the CPU destination model and assistant across requests.** The retained short-workload breakdown records 2.345s CPU target loading and 0.518s assistant loading after GPU prefill, versus61ms KV handoff. Keep reusable weights, metadata and thread pools resident where admission permits; bind a new assistant context only after the target owns the transferred cache. A warm process and warm filesystem cache are different controls. These historical stage times are opportunity sizes, not promised savings. Existing persistent CPU ownership already avoids re-handoff on subsequent tool turns.
2. **Complete visibility once per transfer, not once per view.** Allocation batching already reduced48view acquisitions to2; do not repeat that optimisation. Current public CPU-view creation still synchronises the backend and submits a host-access barrier with a fence wait for each acquisition. Prepare all ranges, batch their visibility work, and use one completion wait; ideally place the barrier in the final GPU prefill submission. Keep the independently callable public view API safe. Coherent memory does not remove GPU execution completion or host-visibility requirements. Need fresh post-batching stage profiling and cancellation/lifetime tests before claiming savings.
3. **Avoid allocating KV storage that will be discarded.** Source init currently allocates ordinary KV then replaces it with shared storage. Destination context allocates empty CPU KV that commit discards when shared views are installed; copy fallback also prepares replacement allocations. Allocate shared source KV directly and provide a metadata-only compatible destination, or reuse a bounded destination pool. Preserve atomic rejection/rollback and reset semantics; reduce peak residency and allocation/clear costs without skipping initialisation safety.
4. **Reduce transition setup and priming.** Prevalidate immutable geometry/identity and prepare destination graph metadata off the critical path while retaining mutable-state checks at commit. The retained caller re-evaluates the last prompt token on CPU to recreate logits and prime MTP hidden state; its historical call duration was112ms. Transferring the small final logits/required hidden activation with explicit ownership could avoid this, but MTP state/order/rollback needs proof. This is more invasive than batching waits; logits alone are insufficient.
5. **Make the fallback copy cheaper.** It currently allocates per tensor and performs1MiB tensor_get→scratch→memcpy chunks. UMA tensor_get can incur a host barrier on each call. A synchronised allocation-level read session and direct copy into prepared destination spans can remove repeated barriers/staging. For unsupported mappings retain bounded staging and consider pipelined transfer. Copying only live spans is possible only with correct ring/SWA holes,positions andfuture writes; do not truncate state by prompt length.
6. **Choose when handoff is worthwhile.** Preserve CPU ownership through the conversation (already done); estimate a cold-prefill threshold from the three-arm benchmark. GPU launch,loading and transition costs may outweigh short-prompt gains. Shared weights or one model with backend-specific execution plans could eventually avoid dual model loads/allocations, but current handoff explicitly rejects shared model residency; this needs an ownership redesign, not a flag flip.

Expected impact is mainly first-token latency, per-request overhead and memory headroom. Higher sustained decode tok/s is not implied: matrix/attention work dominates long decoding, and zero-copy's short-run gain did not persist at4K. Any overlap experiment must preserve the host reserve and measure shared-memory bandwidth contention. No implementation, new admission or benchmark run is authorised by this research note.
