# Gemma prefill and decode optimisation plan

Start from the deployed score3 stack and preserve each validated improvement. Optimise CPU decode and GPU prefill in separate, sequential experiments. Update the baseline ledger as soon as a candidate is validated; deployment is a separate recorded event.

This plan replaces the old timeline checklist on 11 September 2026 at Rui's request. [previous-plan.md](previous-plan.md) archives all 38 old items and retains the incomplete capacity/recovery work. [baselines.md](baselines.md) records the starting stack, measured gains, known limitations and the append-only baseline procedure. Test steps below are **planned**, except the explicit B0 capture and already retained evidence.

## Starting point and operating rules

**B0-score3** is `20260911-score3-stopped`: CPU small-target-batch dispatch, score3 and ATTN4 value tiling, Vulkan FP32/256 prefill, F16 compact KV, FA off, CPU8/prefill16, draft8/16, MTP3. Use its actual loaded hashes and release configuration, not the current checkout revision, as the comparison baseline. The original 8.9341 tok/s observation is historical evidence, not a fresh reference timing for every future experiment.

- Preserve this release and its current operational rollback, ATTN4. At the start of each new maintenance stage, snapshot the **then-current deployed release** as that stage's restore target. The ATTN4 rollback of B0 is not permission to restore ATTN4 after a later B1 deployment.
- Rui intentionally stopped both speech services and instructed uninterrupted testing. No repeated permission polling is needed while that approved state persists. Check both units inactive/dead/PID0, no speech listeners/connections/native workers before and throughout load. Do not restart speech. Unexpected state or command errors fail closed.
- Run CPU/GPU heavy experiments sequentially on the shared-memory/power-limited host. Isolated diagnostic compiles may not overlap timing. No competing delegate builds or inference.
- Maintain at least 6 GiB available RAM and at most 16 MiB swap per trial worker; GPU admission needs 12 GiB before startup. Sample actual owned PID identity, RSS/PSS, swap, MemAvailable, faults, temperature and throttling. Missing/unreadable resource data fails closed. Temperatures >=95 C are annotations; retain hardware protection and do not invent a new thermal abort.
- Use bounded supervised units, exact owned-process handles and automatic current-release restoration. Cancel pending requests first, then TERM/KILL only owned trial children. Wait for the unit/restoration hook to finish before checking current supervisor identity. Never access speech media/transcripts or unrelated private data.
- Historical thread/MTP/FA/Q8/paired-fallback screens stay closed unless a new kernel or workload gives a specific interaction hypothesis. Retained tail1024 and split-K options remain available for their measured scopes.

## Decisions after a setback

| Observation | Required action | What stays valid |
|---|---|---|
| Build include, launcher, case-file or reporting error | Save the failure, fix the smallest cause, test the fix; repeat only affected/missing gates | Prior correctly identified native/timing/quality evidence and already deployed improvements |
| Speech/resource guard, crash, ownership error or NaN/Inf | Stop owned trial; restore the current safe release and verify it; diagnose before load resumes | Unaffected earlier results remain evidence, but this run is incomplete and the failing candidate cannot be promoted |
| One noisy slowdown, overlapping ranges or mixed counterbalanced blocks | Label inconclusive; inspect work counts/environment and run a bounded discriminating follow-up if useful | Candidate patch and confirmed improvements in other scopes; do not disable the whole stack |
| Better tail/short-context result but slower whole request | Keep a scoped research candidate; test a selector only when justified | The measured partial benefit; production retains its better default |
| Reproducible quality or operational regression | Stop promotion; isolate the responsible change, repair or revert only that change where possible | Independent safe improvements; shared baseline failures remain labelled |
| Confirmed benefit plus required correctness/resource gates | Append a validated baseline immediately, with scope and evidence | New candidate becomes the next experimental reference; deployment awaits its serving gates and approval |

Cross-backend greedy token drift remains diagnostic. Do not lower numerical tolerance, rename a generated API or change a task contract to turn a failure into a pass. Conversely, harmless wording drift alone must not erase a valid speed improvement. Minor numerical/performance differences need scope and evidence; hard safety failures are never waived.

## Common run contract and comparison budget

**T01 - Freeze fixtures and harness.** Before load, save input/token hashes, exact evaluated/cached counts, expected answers, output budgets, seeds, model/tokeniser/assistant identities, context/slot geometry and native test-file format. Use the retained 64658-cache/25-evaluated/128-generated fixture as the primary saved64K decode measurement. Discover missing 4K/16K/32K/48K states from existing evidence before generating anything. Record disk space and every new state hash/layout; models/states stay local.

Run helper tests before inference: numeric case loader counts, dimensions/strides, eligibility/reference exclusion, all row/reduction tails, live-map identity, aborted fetch, child ignoring TERM, dead child, stale lock, owned-container cleanup, stopped-speech malformed state/reactivation and fail-closed resource reads. A tested helper is not a claim of all-phase native recovery.

**T02 - Freeze practical quality fixtures.** Prepare two bounded coding tasks with exact exports and a small offline behavioural test suite, plus one source-grounded retrieval task and one four-round tool/cache workflow. Preflight the tests against an independent reference implementation, including wrong export/truncated-output negative controls. No network, secrets or workspace access for generated-code execution. Cap each task at 512 output tokens per turn, four rounds and a 2-second/256-MiB code execution sandbox; record whether enforcement is available before executing generated code. Validate baseline performance on the tasks, rather than assuming success. If a fixture needs repair, version it, retain the original failure and freeze it before candidate comparisons; no per-candidate contract changes.

Measure cold time to first visible token, cold end-to-end latency, native prefill time, sustained generation, warm tool/edit latency, generated tokens and task success separately. TTFT includes scheduling and transfer. Request wall must state whether model startup, tooling and save/restore are included. Report raw runs, medians, ranges, paired differences, failed runs, cache/draft counts and resource traces; do not add gains from unrelated comparisons.

**T03 - Bounded screening and confirmation.** Freeze the exact baseline ID for an entire experiment before load. GPU-causality tests keep the same decoder parent in both arms until that experiment closes, even if a newer decoder is validated meanwhile; use the newest stack separately for operational/interaction checks. A scoped tail-only win becomes a reference only for its named workload, never an unrelated default. Screen at most two justified variants per hypothesis with four uninstrumented runs each: baseline/candidate/candidate/baseline. A useful screen is not confirmation. For the selected finalist, run an independent eight-run ABBA/BAAB block (four per profile) on the primary workload. Fresh-process/slot-reset policy is fixed beforehand. Select the latest validated baseline applicable to the declared scope at experiment start, with runtime/profile source hashes pinned and profiler flags absent; do not change it mid-comparison.

There is no universal minimum percentage gain that discards small improvements. Require matched work, a reproducible primary benefit and a documented secondary-workload trade-off. If the confirmation is materially discordant across blocks or within observed noise, allow **one** extra four-run block addressing the identified uncertainty, with its reason recorded first; otherwise classify inconclusive and move on. Never repeat until a favourable number appears. Secondary contexts use two counterbalanced observations/profile initially; expand only a genuine ambiguity that affects adoption.

For each relevant coded/tool fixture, run baseline/candidate pairs with seeds42 and43 and the same output budget. Newly failing tasks that baseline passes require investigation and block general adoption of that candidate. Shared failures remain failures for both. Small test counts do not establish a 5-percentage-point noninferiority bound. Use same-prefix logits/probabilities and independent answers to investigate drift when it appears; retain top-k/residual limitations if using truncated probabilities.

## Decode track

**D01 - Refresh only the stale profile.** Run one isolated instrumented saved64K decode on B0 (or its latest validated successor), with the same primary fixture. Capture score/value/n1/Q4/Q6-vocabulary node wall, shapes and call counts, conversion/packing thread sums, draft/target phases and scheduler/barrier costs where supported. Require no counter overflow and reconciliation with total matrix wall. If instrumentation scope changes, retain its identity separately; it is never throughput evidence. Target-only or a second context profile is conditional on a specific unresolved question, not a new general MTP sweep.

**D02 - Inspect the hot value kernel.** Check actual F16 n4 dispatch and generated instructions for register spills, repeated conversions/loads, reduction dependencies and work imbalance. Review the full outer gate and source revision. Score3 and the small-batch pool stay enabled. Choose at most two value-specific tile/reduction variants supported by these findings. Do not copy the score3 tile blindly: values reduce across tens of thousands of elements. If the profile points elsewhere, document that change of priority before implementing.

**D03 - Native correctness before timing.** Cover value products with m512, k32768/64768/65024/65536, n1/3/4; add legal widths immediately below/above the candidate's vector/tile divisibility boundary. Use the existing eight-query/two-KV-head broadcasting and both accepted contiguous and strided layouts. Include short-SWA k768/m256 controls, score controls, flag-off and use_ref controls. Use native GGML reference tolerances unchanged; record baseline failures. Trace actual override for eligible shapes and its absence for excluded shapes. Add output canaries/tail coverage tests where supported. Only finite, correctly bounded native results advance.

**D04 - Confirm decode benefit.** Apply T03 at saved64K/128 tokens; repeat a finalist at 512 generated tokens to expose sustained behaviour (four counterbalanced runs initially). Test 4K and32K controls with 128 generated tokens, without regenerating completed states unnecessarily. Keep cache policy, all thread pools, MTP and sampling fixed. Separate pure generation from the 25-token prompt tail. Run the frozen coding/retrieval/tool comparisons and inspect any new quality difference. A kernel-only gain that loses request latency stays scoped or experimental.

**D05 - Validate and record B1-decode.** Save/restore on the same CPU, finite64K scan, final-token continuation, MTP continuation, independent tool slot and preserved long append. Check reference/layout/EOF, no foreign or missing cells, zero worker swap and correct cache growth. Record validated scope, limitations and parent B0 before any next experiment. If adopted and serving checks pass, append deployment verification; otherwise retain B0 production and identify B1 as experimental only.

**D06 - Conditional next bottleneck.** Only if the refreshed profile after an accepted value change makes Q4 projections or the Q6 vocabulary projection a material remaining cost, investigate one narrowly gated packing/matrix candidate under D02-D05. Preserve accepted attention kernels; no repeat of the known n1 paired-fallback experiment without a new implementation or workload question.

## Prefill track

**P01 - Establish a usable crossover experiment.** First inspect the live FP32/256 GPU profile, state geometry and native APIs. A max1024 allocation sliced into256 requests may differ from the real max256 baseline; measure/record that factor rather than assuming equivalence. Determine whether changing active microbatch scheduling within one worker can avoid reload and preserve compact-SWA capacity. If existing APIs cannot do this, plan the smallest isolated scheduler change and label its fixed allocation policy. Do not claim dynamic batching from a command-line switch that requires restarting the worker.

**P02 - Measure missing positions, not the completed broad screen.** Use identical-prefix checkpoints around16K,32K,48K and the retained64K result. At each missing position, compare256/1024 using the same 1022-token suffix and measured actual microbatches, first four counterbalanced runs/position. Reuse old64K evidence for direction; add a current-profile control only if runtime/layout changes invalidate comparability. Record GPU timestamp/operator time and CPU wall, residency/allocation, actual cache/evaluated counts and memory. Profile one informative crossover/tail case to identify attention versus projection/softmax cost. No crossover is assumed at32K.

**P03 - Test a supported phase selector.** Only if P02 shows a repeatable crossover, choose a threshold from those screens and freeze it before confirmation. Test256-before/1024-after against fixed256, with full request-token coverage, no duplicate/omitted positions and no worker reload hidden from timing. Native/layout tests cover threshold-1/threshold/threshold+1, final partial batch and switching over SWA-ring wrap. Keep export bounded to the validated CPU destination history (current cap768); reject missing history or invalid v3/v2 conversion. If larger allocation erases the gain, retain the tail candidate instead of forcing promotion.

**P04 - Confirm whole-prefill benefit.** First complete one fresh64663-token finite handoff screen per profile. If beneficial and safe, run an independent four-request ABBA whole64K confirmation, each with reset owners and identical cache policy; use one additional counterbalanced block only for a recorded ambiguity. Treat these as long runs with per-stage time caps, not an overnight unlimited sweep. Also compare cold4K/16K/32K controls (two/profile initially). Measure startup, GPU prefill, save, conversion, CPU restore, first token and end-to-end separately. All original recall keys, CPU final-token-only evaluation, finite state and long append must pass. Tail improvement alone cannot update the whole-prefill baseline.

**P05 - Conditional GPU kernel work.** If batching is not useful or a substantial attention hotspot remains, use the current FP32 profile to select at most two device/shape-specific workgroup, load or reduction variants. Native long score/value, short controls, boundary dispatch, reference accumulation and finite handoff precede T03 and P04 timing. The exact IrisXe device gate and FP32 accumulation stay fixed unless precision itself is the declared experiment. Split-K/FA/Q8 global sweeps are not reopened without a new hypothesis.

**P06 - Validate and record B2-prefill.** Append the validated whole-prefill or explicitly scoped tail result with parent baseline, complete timing boundaries, resource cost and regressions. Do not attribute a CPU improvement to GPU prefill. Use the newest validated decoder for operational tests, while preserving the fixed decoder used for causal GPU comparisons.

## Integration, recovery and deployment

**I01 - Combine accepted changes deliberately.** If decode and prefill variants were independently validated against different parents, record both parents. Run baseline versus combined native/layout controls plus one fresh64K handoff pair, a 512-token saved-state decode pair and the frozen warm/coding/tool tasks. Expand a discordant interaction only as needed; do not rerun every historical screen. Commit the combined baseline only when the interaction checks pass.

**I02 - Close affected native lifecycle gaps.** Reuse valid historical GPU-kill fallback/CPU-generation-restart evidence when the worker code is unchanged. For changed paths, test cancellation while queued, during GPU startup/prefill/save/convert/restore and CPU generation; GPU SIGKILL before handoff, CPU SIGKILL with supervisor restart, two-owner alternation/eviction, stale partial transfer cleanup and stop/timeout restoration. Require bounded return/drain, no orphan, no stale owner reuse and no duplicate response replay after SSE begins. External tools are not executed by the adapter, so do not promise exactly-once tool execution. A failed phase stays explicitly unqualified without invalidating unaffected validated speed gains.

**I03 - Capacity is a separate claim.** Verify two owners at moderate occupancy first, then increase populated contexts stepwise through32K/64K where safe. Attempt near128K per owner and fallback only after measured memory projections meet the reserve and native context permits it. Record actual occupied tokens, not configured capacity. Abort on the same resource rules; document a safe supported envelope if full dual128K does not fit. Capacity failure does not erase a safe single64K optimisation.

**I04 - Rolling adoption loop.** For each independently validated improvement, review owner approval and affected serving/resource gates; do not wait for all unrelated research/capacity questions. Pin an immutable release, arm timed rollback to the then-current deployment, perform one cold SSE/tool/cache smoke with stopped-speech/reactivation and detailed PID/swap checks, then verify actual maps/argv/flags/health/idle slots. Cancel rollback only after success. On failure restore the current safe deployment and repair the missing gate; keep the validated candidate and all unaffected changes.

**I05 - Baseline closeout after every accepted increment.** Append manifest, individual observations/medians and exact fixture scope to the ledger; preserve the previous baseline. Record both a causal comparison parent and the then-current production ID. If the candidate's parent is production, its normal confirmation supplies that matched comparison; otherwise run the affected primary workload against current production as an integration check before adoption. Do not rerun original B0 for every increment; a matched B0/latest comparison is needed only for a cumulative claim. Distinguish validated, adopted experimentally, deployed, held and superseded states. If later integration or serving checks fail, append a held/restricted/revoked-reference event; retain the passing scope, but new work in the affected scope returns to its last safe parent. Reproducible safety or corruption findings suspend that candidate's reference eligibility until fixed and revalidated. A fixture/launcher defect invalidates only the evidence it actually affected, not all candidate results. Refresh the next stage's baseline and restoration paths, current plan and notes. Commit/push only task-owned source/evidence to the verified rcarmo fork, check a Git archive contains every manifest file, run its offline verifier and attach a concise report. Never claim cumulative gains without a matched original/current comparison.
